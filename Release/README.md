# Local release safety

Generated **DemoAssets are local-only for every tool**. Never version them or upload them to GitHub, separately or inside application archives. Offline demo source/profile/launchers and normal runtime branding remain distributable.

`New-WorkplaceCloudHubReleaseZip.ps1` accepts an explicit file list, excludes DemoAssets directories and media archive names at every depth, and rejects embedded ZIP/NuGet archives containing DemoAssets. Preview is the default; `-Build` creates a new ZIP without replacing existing files.

`Publish-WorkplaceCloudHubRelease.ps1` checks every explicit asset, nested ZIP/NuGet content and release-note archive references before invoking GitHub CLI. Without `-Publish`, it only validates locally and does not run Git or GitHub CLI. An explicit repository, tag and full commit SHA are required. Existing releases are never clobbered by this wrapper.

Standalone product packagers embed the same two functions from `WorkplaceCloudHub.ReleaseSafety.ps1`, avoiding a new runtime dependency in distributed tools. Regression tests compare those function bodies and exercise contaminated inputs. Archive inspection fails closed on corruption, depth greater than eight, more than 100,000 entries or more than 512 MiB of inspected uncompressed data. No archive is extracted by the guard.

Build and upload through these guarded entrypoints; do not use wildcard uploads or attach whole local output directories. This code does not prevent a person from bypassing it with a direct `gh` command; the repository policy also applies to manual publication.

## Standard release-note footer

Every release body ends with a link to the website so readers can find the product documentation. The publish wrapper refuses notes that contain no `https://workplacecloudhub.com/` link. Use the tool product page when one exists, otherwise the tools catalog:

```markdown
---

Product page: [<Tool name>](https://workplacecloudhub.com/tools/<tool-slug>/) | More tools: [workplacecloudhub.com/tools](https://workplacecloudhub.com/tools/)
```

| Release tag prefix | Product page slug |
| --- | --- |
| `endpoint-diagnostics-analyzer-v` | `smart-endpoint-diagnostics-analyzer` |
| `smart-intune-remediation-manager-v` | `smart-intune-remediation-manager` |
| `device-reboot-manager-v` | `smart-device-reboot-manager` |
| `device-registration-tool-v` | `smart-device-registration-tool` |
| `endpoint-migration-toolkit-v` | `smart-endpoint-migration-toolkit` (generated by the toolkit release builder) |
| `sharepoint-migration-toolkit-v` | `smart-sharepoint-migration-toolkit` |
| `exchange-user-notifications-v` | `smart-exchange-user-notifications` |
| `exchange-migration-readiness-v` | `smart-exchange-migration-readiness` |
| `smartworkplaceintelligence-v` | `smart-workplace-intelligence` |
| `smartfinops-workplace-v` | `smartfinops-workplace` |
| `smart-thinclient-v` | `smart-thinclient` |

Retired projects do not get a product page link.

The table is mirrored in `website-footer-map.json` (a test keeps both in sync). As a safety net, the `Release website footer` GitHub Actions workflow runs when a release is published: if the body contains no `https://workplacecloudhub.com/` link, `release_website_footer.py` appends the footer for the tag prefix (tools catalog only for an unknown prefix, nothing for `noProductLink` prefixes). Drafts are not touched. Still write the footer in the notes file: the workflow is a fallback, not the normal path.
