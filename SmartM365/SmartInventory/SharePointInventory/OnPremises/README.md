# SharePoint Server 2016/2019 inventory

Two independent, read-only Windows PowerShell 5.1 x64 collectors run on a SharePoint farm server. They require the SharePoint Management Shell snap-in and administrator-prepared SharePoint Shell access. They never grant permissions or change SharePoint locks. They do not run through the SmartInventory orchestrator.

## Collectors

- `SmartM365-SharePoint-OnPrem-Infrastructure-Inventory.ps1` writes `SharePoint_OnPrem_Farms.csv`, `Servers.csv`, `ServiceApplications.csv`, `WebApplications.csv`, `WebApplicationZones.csv`, and `ContentDatabases.csv` with the common `SharePoint_OnPrem_` prefix.
- `SmartM365-SharePoint-OnPrem-Content-Inventory.ps1` independently discovers web applications and content databases and writes `SharePoint_OnPrem_SiteCollections.csv`, `SiteAdministrators.csv`, `Webs.csv`, and `CollectionCoverage.csv`.
- Each script has its own local JSON template, run folder, log, receipt, current CSV publication, and weekly history. `FarmId`, `WebApplicationId`, and `ContentDatabaseId` are shared join keys. Content does not consume Infrastructure CSVs.
- `Get-SPWebApplication` selects content applications by default and excludes Central Administration. `IncludedWebApplicationUrls` and `ExcludedWebApplicationUrls` in each local JSON narrow the scope. Empty inclusion means all content applications.
- Both templates set `EnableSharePointUpload=true` by default. A published full or partial run uploads its timestamped and current CSVs through SmartM365.Core; Core also uploads the source receipt and logs when configured. Content writes separate weekly history for qualified and Partial runs. This includes owner and administrator logins in Content CSVs. Set `EnableSharePointUpload=false` in a collector's source `local.json` to disable it. `-ValidateOnly` and Content `-MaxItems` disable upload for that run.

Infrastructure sends an HTML summary using the shared SmartM365.Core email frame, KPI cards, and table renderer. It includes farm edition/build, collection health, conditional alerts, servers, web applications, authentication by zone, and, for qualified runs, a `Files` table with the row count of each of the six CSVs. The Servers card counts SharePoint members only (`Role != Invalid`) and shows the number of external entries separately; the Servers email table and server health alerts include SharePoint members only. The Servers CSV retains every `Get-SPServer` row, including `Role=Invalid` entries for external services. URL and application-pool cells do not wrap within words in the Outlook-compatible HTML table. The largest-database table is omitted until measured database sizes exist. A delta is shown only when the previous completed source receipt verifies all six file hashes and row counts and the CSVs share one run ID, tenant key, and farm ID. The receipt run ID identifies the receipt and is not required to equal the CSV run ID. The Servers delta compares SharePoint members only. Missing or incompatible previous evidence silently omits the delta. The build-to-edition lookup is the explicit `SharePoint-OnPrem-BuildEditions.psd1` list derived from [Microsoft's SharePoint update history](https://learn.microsoft.com/en-us/OfficeUpdates/sharepoint-updates); unknown builds display `Unknown`. Update the list from the Microsoft release table when a new build is deployed.

Infrastructure sends at most one qualified summary and one issue summary (Partial or Failed) per local day. The two markers in its tenant-specific `OutputRoot` are independent and protected by exclusive file locks. `-ForceMail` bypasses either daily gate; `-ForceSendDailySummary` remains an alias for existing commands. `-ValidateOnly` never sends mail. A failed mail attempt leaves its marker unchanged, logs a warning, and does not change the CSV, receipt, or collection exit status. A configuration failure before the tenant context and Core mail transport are loaded cannot send mail. HTML uses the existing Graph `SendEmailHtmlReport` path, without a MIME plain-text alternative. Set `From`, `To` (or `ErrorMailTo`), `AppId`, `TenantId`, and `Thumbprint` in the tenant or collector `local.json` before a full run. The app needs `Mail.Send` scoped to the approved sender mailbox; SharePoint upload needs `Sites.Selected` with the site-level write grant. The marker and lock files are local output metadata, not SharePoint changes.

Content now uses the same Core HTML email frame, KPI cards, and tables. Its summary shows selected web applications and databases, observed site collections, webs, coverage issues, read-only collections, unverified locks, upload failures, bounded examples of coverage and read-only cases, and per-CSV row counts when current CSVs were published. An early failure, including an occupied source-receipt lock, shows unobserved values as `n/a` and sends a Failed issue mail. Qualified and issue (Partial or Failed) mail have separate daily markers; `-ForceSendDailySummary` and its `-ForceMail` alias bypass the relevant marker. `-ValidateOnly` and `-MaxItems` send no mail. Mail delivery failure is logged without changing the inventory result. Ctrl+C sends no mail.

Full runs install only `Microsoft.Graph.Authentication` from PSGallery with `Scope=CurrentUser` when it is missing, then import it for upload and Graph mail. Windows PowerShell 5.1, .NET Framework 4.7.2 or later, PowerShellGet, and access to PSGallery are required for automatic installation. A failed installation is logged as a warning and does not discard local farm inventory; upload and mail remain incomplete until the module is available. Content `-MaxItems` and both `-ValidateOnly` modes do not install Graph. Existing source `local.json` files keep their saved values, but these two daily summary emails explicitly use Graph even if an older `SendMailMode` value says SMTP.

Every CSV includes `TenantKey`, `FarmId`, `RunId`, and `CollectedAtUtc`. Infrastructure files contain farm build and counts (`Farms`), server identity/role/status (`Servers`), service application identity/type/pool (`ServiceApplications`), application URL/pool/database count (`WebApplications`), zone URL/authentication (`WebApplicationZones`), and database identity/server/site count/read-only status (`ContentDatabases`). `ContentDatabases` adds `DatabaseSizeBytes`, `DatabaseSizeStatus`, `NeedsUpgradeIncludeChildren`, and `NeedsUpgradeStatus`. `DatabaseSizeBytes` is intentionally empty and `DatabaseSizeStatus=Unavailable`: SharePoint's [DiskSizeRequired](https://learn.microsoft.com/en-us/previous-versions/office/developer/sharepoint-2010/ms480088(v=office.14)) is a backup-space estimate, not the measured database size, and this lot makes no SQL query. `NeedsUpgradeIncludeChildren` is read from the already enumerated `SPContentDatabase`; a missing or unreadable value remains empty with `PropertyUnavailable` or `ReadFailed` in `NeedsUpgradeStatus`, never a default `False`. Microsoft's [SharePoint Server 2016](https://learn.microsoft.com/en-us/sharepoint/upgrade-and-update/upgrade-content-databases) and [2019](https://learn.microsoft.com/en-us/sharepoint/upgrade-and-update/upgrade-content-databases-2019) upgrade documentation shows this property in `Get-SPContentDatabase`; live behavior on each installed build still requires farm validation. The existing source receipt automatically records and hashes the changed CSV; its six-file registry entry is unchanged. Content files contain collection identity, owner, size, quota, modification, template, language and lock observations (`SiteCollections`); administrator logins and owner flags (`SiteAdministrators`); web identity, template, list/library counts and permission inheritance (`Webs`); and one coverage result per attempted collection or database failure (`CollectionCoverage`). The exact column lists are declared in each collector's `$schemas` block.

Infrastructure reads the farm configuration database name from `SPFarm.ConfigurationDatabase.Name` when available. If that property is empty, it queries `Get-SPDatabase` and accepts exactly one database whose `Type` is `Configuration Database`. An unavailable or ambiguous name remains blank and prevents current publication; the run log lists each coverage failure. After CSV generation, the Infrastructure log names the effective weekly history root and, on failure, the publication stage, destination path, and PowerShell error location.

## Publication and qualification

The SharePoint on-prem CSVs are intended for SmartWorkplaceIntelligence Power BI reporting. The collectors are not registered as SmartWorkplaceCMDB sources, and Power BI model integration is outside this collector change.

The scripts write run CSVs first. Empty datasets have headers. Infrastructure promotes current CSVs into tenant-specific `DATA-LAST` only after full collection. Content promotes the CSVs when collection reaches the end of the selected databases, including when `CollectionCoverage` records site or database anomalies. Its generic configured-output receipt has `Status=Completed` after the four current CSVs pass row, hash, and tenant checks. It does not qualify farm-wide completeness: `IsPartialInventory` is null and `FullInventoryQualified` is false for this receipt type. Consumers requiring complete Content coverage must inspect `CollectionCoverage` for the same `RunId` and reject any non-`Collected` status. The run log, summary email, and warning exit code 3 also identify incomplete coverage. A fatal global timeout or a publication failure leaves the previous receipt intact. A current CSV upload failure after local publication leaves its receipt intact and ends the run with warnings (exit code 3).

For a full Content run, each database's observed site collection count is compared with `CurrentSiteCount`. An unavailable count or mismatch creates a `CollectionCoverage` database status; the error message includes expected and observed counts. A database read error is recorded as `DatabaseEnumerationFailed`. Per-collection failures remain visible in both `SiteCollections.CollectionStatus` and `CollectionCoverage.Status`. Missing metadata is named in `CollectionCoverage.ErrorMessage`. These issues produce a partial current publication (exit code 3), never a complete inventory claim. With weekly history enabled, the first Partial snapshot of an ISO week is saved separately under `Content\WeeklyHistory\Partial\YYYY-Www` with all four CSVs and a manifest labeled as incomplete coverage. `CollectionCoverage.csv` names every observed anomaly, and the current receipt keeps `FullInventoryQualified=false`. A later Qualified run can create the standard `Content\WeeklyHistory\YYYY-Www` snapshot independently. A partial-history save or upload failure is logged and does not block current CSV publication. `-MaxItems` remains test-only and never promotes current CSVs, a receipt, or weekly history.

Content `-MaxItems N` processes at most N site collections across the selected databases. It writes only to a timestamped run folder under `OutputRoot\TEST`, marks the run limited, and leaves `DATA-LAST`, weekly history, the source receipt, and SharePoint upload unchanged. `-ValidateOnly` checks the PowerShell host, SharePoint Shell access, selected content applications, and databases without traversing any site collection, publishing a CSV, or uploading files.

Content has cooperative `-GlobalTimeoutMinutes` (default 720) and `-CollectionTimeoutMinutes` (default 60) checks between SharePoint calls. A single blocked SharePoint object-model call cannot be interrupted safely inside this process. An isolated child-process timeout is outside this lot. A timed-out or inaccessible collection is recorded in `CollectionCoverage`; later collections continue when the process is responsive. A global timeout stops subsequent collection and prevents current publication.

Ctrl+C stops either collector when the active PowerShell or SharePoint call returns control to the host. The interruption path disables further SharePoint upload and mail, records `FailureStage=Interrupted` in the local execution summary, marks an in-progress source run as failed, and releases its source receipt lock. It keeps the timestamped run files for diagnosis; it does not promote a new receipt after interruption. A SharePoint object-model call that never returns cannot be stopped gracefully by this in-process handler. If a later run reports that the `.collection.lock` file is in use, check for an active collector process before retrying; the lock file's presence alone does not mean its handle is still held. If Ctrl+C occurs during the multi-file `DATA-LAST` copy, inspect the current CSVs against the last completed source receipt before treating them as one complete run.

Lock inspection reads `SPSite` and `SPContentDatabase` properties and uses the read-only, server-side `Get-SPSite -ContentDatabase ... -Filter` query for each of the four lock states. Both full and limited runs query only the content databases reached by the run; `-MaxItems` limits detailed site traversal and CSV rows, while lock-state queries may enumerate site IDs elsewhere in a reached database. The exact filtered state is joined by site collection ID. Boolean values never infer `LockState`, because they do not safely distinguish `Unlock`, `NoAdditions`, `ReadOnly`, and `NoAccess`. A missing or conflicting state leaves `LockState` blank and `LockStatus=Unverified` or `Conflict`, and is recorded in `CollectionCoverage`. `IsReadOnly`, `ReadLocked`, `WriteLocked`, `LockIssue`, and `ContentDatabaseIsReadOnly` are retained as separate observations. Query errors and conflicts are logged; no lock is changed. The filtered state, quota units, storage measurement, and administrator enumeration still need a live read-only check on both SharePoint 2016 and 2019 before the output contract is frozen. No `Set-SPSite` or other write cmdlet is called.

## Manual commands

Run from a SharePoint farm server after the administrator has prepared the local tenant configuration and SharePoint Shell rights. Replace `<SmartM365Root>` with the deployed path. Each launcher copies this collector folder, `Config`, and `SmartM365.Core` to its own local cache before invoking Windows PowerShell 5.1. The caches are separate for Infrastructure and Content. The launchers default to `prod`, forward additional parameters, and return the collector exit code.

Copy each `*.local.json.template` to the same basename ending in `.local.json` in the deployed source tree on the share, then review the tenant paths and optional `IncludedWebApplicationUrls` / `ExcludedWebApplicationUrls` arrays. The launchers rebuild their local caches on every run, so edits made only in `C:\ProgramData\SmartM365\LauncherCache` are discarded. Configure `WorkspaceRootPath` or the resolved `DataAllRootPath` in the source tenant configuration to a persistent location outside the launcher cache; a resolved output path inside the disposable cache is rejected. Nested path tokens such as `{{DataAllRootPath}}`, `{{WorkspaceRootPath}}`, and `{{ProfileKey}}` are resolved before path validation. Before a full run, configure `SharePointSiteHostname`, `SharePointSitePath`, `SharePointLibraryDisplayName`, `SharePointTargetFolderPath`, `AppId`, `TenantId`, and `Thumbprint` in the source tenant or collector configuration. An existing source `local.json` with `EnableSharePointUpload=false` keeps that explicit value until changed.

```powershell
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Infrastructure-Inventory.cmd" -ValidateOnly
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Content-Inventory.cmd" -ValidateOnly
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Infrastructure-Inventory.cmd"
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Content-Inventory.cmd" -MaxItems 2
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Content-Inventory.cmd"
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Infrastructure-Inventory.cmd" -ForceSendDailySummary
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Infrastructure-Inventory.cmd" -ForceMail
& "<SmartM365Root>\SmartInventory\Launchers\OnPremises\Start-SmartM365-SharePoint-OnPrem-Content-Inventory.cmd" -ForceSendDailySummary
```

Run each collector on 2016 and 2019 separately. Inspect the two `-ValidateOnly` results before limited or full runs. The `-MaxItems 2` run is not a complete-farm qualification.
